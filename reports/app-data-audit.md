## 优先修复

### 1. 去重键会丢失不同作品

`scripts/build.py:123` 按 `(title, author)` 保留注解字段更多的一条。这不能识别同一个作者的同题作品，也没有合并其他记录的标签、来源和非空注解。

已确认的例子：

- 杜甫《绝句》原库分别存在“迟日江山丽”“江边踏青罢”“两个黄鹂鸣翠柳”三个不同正文，当前包只保留了第三个。
- 李商隐《隋宫》原库分别存在“乘兴南游不戒严”和“紫泉宫殿锁烟霞”，当前包只保留了前者。

对应当前条目标题和作者，原库共有 **65 组不同正文候选**。其中也包括字形、异文、标点附注和源数据问题，不能把 65 组都直接当成丢失作品。

建议：回到原库重做作品识别，用来源 URL、作者身份、规范化正文共同判断；同题不同文保留，疑似异文进入核对清单。保留现有 ID 和旧 ID 映射，避免 App 更新后收藏失效。正文哈希可用于查重，作品主 ID 应独立于正文修订。

### 2. “完整”只检查非空，掩盖了无效内容

以下字段去掉标点、空白后与正文完全相同：

| 条目 | 有问题的字段 |
|---|---|
| 论语十二章 | appreciation |
| 游山西村 | appreciation |
| 遣悲怀三首·其二 | appreciation |
| 赠汪伦 | appreciation |
| 长相思·山一程 | translate |

`merge_annotations.py` 只补空字段，因此原有的无效文本会一直保留下来；其中一些条目虽然有 `ai_generated=true`，问题字段仍来自原始数据。`complete=true` 不应被 App 用来表示内容已经审核。

另有《遣怀》赏析出现 Unicode 替换字符“�”，需回查生成记录或来源修订，不能盲目删字符。

建议：先标记无效字段并进入修订队列，保持原始值和修订记录。把“字段齐全”“结构校验通过”“内容已审核”分开。原始抓取内容与 AI 内容都适用同一套质量检查。

### 3. 正文版本、序言和段落没有建模，逐句对照会错位

- **10 条**正文含明确的多个版本标记。例如《题破山寺后禅院》串联四个版本，共 16 段，而译文与注释各 4 段。
- **19 条**译文或注释行数与正文不等：译文 16 条，注释 9 条，有重叠。其中 16 条带 AI 标记，3 条没有。
- **162 条**正文含“一作”“通：”“版本”等提示文本；这是一项候选统计，具体需要逐条判断。
- 数组元素的含义混杂：一联、一段、整章、序言都有。《静夜思》是两联两个元素，《木兰诗》是长段落，《观公孙大娘弟子舞剑器行》第一段是序言。

因此，即使数组长度相同，也不能单凭下标证明语义对齐。给下标加越界保护只能避免崩溃，仍可能把译文放到错误的句子下面。

建议：保留抓取原文；独立保存正文主版本、异文、序言和附注。为显示单元设稳定 ID、顺序与类型，并让译文/注释明确引用单元。暂未核对的内容使用明确的“整篇/整段说明”模式，不伪装成逐句注解。不要直接用标点切分并覆盖现有对照。

### 4. 当前脚本不能重建当前交付包

- `build.py` 的输出目录是脚本目录 `scripts/`。
- `build_v2.py` 从项目根目录读取 `poems_lite.json`、`authors.json`，实际文件在 `raw/`。
- `build_v2.py` 输出到 `scripts/v2/`，合并脚本却只更新 `app-data/`。
- 多个工具写死了本机绝对路径。

建议：用项目相对路径和命令行参数统一入口，明确 `原库 → raw → app-data → 校验 → 发布`。构建在临时输出目录完成并通过检查后再替换交付包，JSON 与 SQLite 从同一份规范化数据导出。重建必须能够复用并验证已有生成记录，无需重新调用模型。

## 数据契约需要补齐

### 作者、朝代与分类

- **13 条**没有作者关联，包括《敕勒歌》《今日歌》《沁园春·长沙》等。不能只在 UI 上遮住简介空白，还应明确未知作者、编纂书名和真实作者的区别。
- **16 条**作品与作者朝代不同，包括曹植、曹操等条目。部分可能是跨朝代标签口径不同，需要核对，不能直接把一侧覆盖到另一侧。
- **1170 条**文体只写“古诗词”，不支持可靠的诗、词、曲、文筛选。
- 《论语十二章》《三峡》《廉颇蔺相如列传(节选)》《核舟记》《卖油翁》等古文仍存在；README 的“纯诗词”表述不准确。可保留古文并正确分类，也可按产品范围排除；不要因为“文言文”学段标签就删除《木兰诗》等诗歌。
- 题材被截成高频前 40 项，导致 **971 条**丢失部分原始标签，**274 条**没有题材。“田园”“月亮”“写雨”等有价值标签也被丢弃；“小学生必背古诗70首”却混入题材。
- JSON 有 `levels`，SQLite 没有学段字段或关系表；选集则存为分隔字符串。

建议：数据库保留完整分类关系，由前端决定显示哪些热门标签。选集、题材、学段各有明确类型，关联表去重并加外键。作者作品数区分“来源宣称总数”和“当前包实际收录数”。

### 来源与审核

1470 条在 raw 中都有来源 URL，但发布 JSON/SQLite 没有保留。1358 条带 AI 标记的作品中，**440 条**同时保留了原始注解，单个布尔值无法表达每个字段的来源。

建议至少记录：来源记录 ID、来源 URL、原始值；注解类型、来源类型、模型与生成批次、生成时间、审核状态、修订版本。授权依据需要单独记录，不能由“原文”“抓取”“AI”标签推导。

若 JSON 也作为独立交付格式，应提供仅含当前关联作者的 `authors.json`；目前作者简介只随 SQLite 交付，raw 作者文件包含全部 7729 位作者，且 ID 口径不同。

### 搜索

目前逐字索引能支持普通中文检索，但需要统一查询函数：

- 按 README 拼接 `明月"` 会出现 `unterminated string`。SQL 参数绑定与 FTS 查询表达式转义是两件事。
- 索引删除标点后，“明月”会命中《鸡鸣》的“匪东方则明，月出之光”。所以 48 条 FTS 命中与 47 条字面连续命中不同，需明确产品语义。
- 标题中的别名，如“草 / 赋得古原草送别”，最好保留完整来源标题并拆出可搜索别名。
- 若后续允许修改正文，应同步更新 FTS；当前没有同步触发器。

上线前在目标 App 运行环境验证 FTS5 支持、中文查询、特殊字符、空查询、分页与排序。简繁转换、拼音检索按产品需要增加，并与展示原文分开。

### 发布与更新

SQLite `user_version=0`，尚无数据包版本与迁移约定，也没有外键声明。建议补上：

- `schema_version`、`data_version`、构建入口、来源版本、条数与文件 SHA-256。
- 发布前校验：关系完整性、JSON/SQLite 一致性、有效注解、对照模式、FTS 同步。
- 收藏、历史、背诵进度独立存储，并用稳定作品 ID 关联。
- README 从构建统计更新：当前 AI 标记 1358 条、待补文件为空；旧文档仍写 1357 条和“剩 1 首”。

## 推荐实施顺序

1. 修复构建路径与去重规则，保留旧 ID 映射；从原库恢复被误合并作品。
2. 修订 5 处原文冒充注解、乱码与混合版本；为未对齐内容标注对照模式。
3. 补作者关系、学段表、完整标签、字段来源和审核状态。
4. 统一安全查询入口，生成带版本及校验信息的数据包，更新使用说明。
5. 根据 App 功能再补拼音、多音字校读、朗读资源、名句、背诵和教材目录；这些不应成为清理基础结构的前置条件。

## 复查命令

```powershell
python -X utf8 scripts/audit_data.py
```

脚本只写 `reports/app-data-audit.json`。退出码 1 表示检测到发布阻断项；本次结果为 **9 类 error、10 类 warning**。这表示问题类别数量，各类可能涉及多条记录，也可能重叠。原库不存在时跳过原库碰撞检查，并在摘要中标记 `original_dump_scanned=false`。

脚本能检查结构和可机械判断的污染，不能自动证明古诗文的释义、典故和历史背景正确。候选异文与语义准确性仍需内容核对。
